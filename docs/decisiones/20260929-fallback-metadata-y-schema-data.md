# Decisión: ejecución de consultas APEX y propietario DATA por defecto

- **Fecha:** 2026-09-29
- **Estado:** vigente
- **Objetivo:** evitar que una limitación de ubicación de archivos en el MCP se reporte como falta de acceso a metadata, conservar una lectura directa incluso si falla el helper de contexto y evitar que una creación sin owner explícito caiga accidentalmente en el esquema de `SESSION_USER`.
- **Evidencia:** en Producción la identidad verificada era `DDELACRUZ` en `ZAI`, con workspace `DE` y parsing schema `DATA`. El helper de contexto devolvió ORA-20987. El MCP controlado devolvió `INVALID_ARTIFACT` porque la consulta temporal estaba en el checkout del proyecto `apex.zml`, mientras `workspace_sql_file()` valida que el archivo exista bajo `ROOT` del servidor (`apex.skills`); por eso la consulta no llegó a Oracle. La skill de automatización de esquemas decía que el owner predeterminado era el usuario conectado, en conflicto con `oracle-data-change-governance-final`, que establece `DATA` para objetos oficiales.
- **Decisión:** los diagnósticos APEX verifican destino e identidad, tratan ORA-20987 del helper como fallo de esa comprobación y continúan con una consulta directa a vistas públicas. `execute_readonly_query` acepta una sentencia SELECT con binds enteros, la envía en una transacción Oracle de solo lectura y registra únicamente un hash conjunto de SQL y binds, sin exigir un artefacto en el checkout. Esta ruta se reserva a consultas conocidas de metadata: una transacción de solo lectura bloquea DML directo, pero no es un sandbox para funciones con efectos laterales invocadas desde SELECT. `execute_sql_file` se reserva para artefactos; si el proyecto está fuera del checkout del servidor, crear el temporal dentro del checkout y pasar una ruta relativa. Las skills Oracle crean objetos en `DATA` por defecto, califican el owner en el DDL y solo lo cambian si el usuario especifica otro. Una denegación Oracle se reporta; nunca se reintenta bajo el owner del usuario conectado.
- **Alternativas consideradas:** tratar ORA-20987 como rechazo de la vista; repetir el mismo artefacto absoluto; pedir al usuario ejecutar la consulta; dejar el owner al usuario conectado; resolver la ruta interna de forma explícita y usar la ruta APEX equivalente; fijar `DATA` sin override. Se eligen rutas alternativas dentro del ambiente solicitado y `DATA` con override explícito.
- **Impacto y dependencias:** actualiza las instrucciones de diagnóstico y la documentación del MCP, añade una herramienta SQLcl para SELECT de solo lectura y fija una prueba de regresión para el owner predeterminado `DATA`, conservando overrides explícitos. No altera grants, credenciales, objetos Oracle ni archivos de ambiente. Las operaciones siguen dependiendo de los privilegios efectivos de la credencial y la herramienta.
- **Riesgos y compatibilidad:** las consultas SELECT directas se envían en una transacción Oracle de solo lectura, exigen una sola línea física y rechazan caracteres de control, comentarios, sentencias múltiples y `FOR UPDATE` para impedir que SQLcl interprete comandos de cliente desde la entrada. Esto bloquea DML directo, pero no necesariamente los efectos laterales de funciones invocadas desde SELECT, por lo que el workflow limita su uso a consultas conocidas de metadata. Herramientas APEX y vistas públicas pueden variar por versión o grants. El owner `DATA` debe ser permitido a la credencial; si no, Oracle devuelve la denegación real y la skill no crea el objeto en otro esquema. No se ejecutan mutaciones para probar permisos.
- **Validación:** inspección de código confirma que `workspace_sql_file()` compara la ruta resuelta con `ROOT`; pruebas unitarias cubren la ruta SELECT sin helper de contexto, binds, modo de transacción de solo lectura, rechazo de escrituras y owner `DATA`. No se ejecutó una consulta de producción ni DDL nuevo como parte de esta decisión.
- **Reversión:** revertir los cambios de texto y esta decisión; no requiere rollback Oracle/APEX.
