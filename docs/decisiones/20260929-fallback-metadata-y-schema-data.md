# Decisión: ejecución de consultas APEX y propietario DATA por defecto

- **Fecha:** 2026-09-29
- **Estado:** vigente
- **Objetivo:** evitar que una limitación de ubicación de archivos en el MCP se reporte como falta de acceso a metadata y evitar que una creación sin owner explícito caiga accidentalmente en el esquema de `SESSION_USER`.
- **Evidencia:** en Producción la identidad verificada era `DDELACRUZ` en `ZAI`, con workspace `DE` y parsing schema `DATA`. El helper de contexto devolvió ORA-20987. El MCP controlado devolvió `INVALID_ARTIFACT` porque la consulta temporal estaba en el checkout del proyecto `apex.zml`, mientras `workspace_sql_file()` valida que el archivo exista bajo `ROOT` del servidor (`apex.skills`); por eso la consulta no llegó a Oracle. La skill de automatización de esquemas decía que el owner predeterminado era el usuario conectado, en conflicto con `oracle-data-change-governance-final`, que establece `DATA` para objetos oficiales.
- **Decisión:** los diagnósticos APEX deben verificar destino e identidad, tratar ORA-20987 del helper como fallo de esa comprobación y continuar con una consulta directa a vistas públicas mediante el MCP APEX verificado. Cuando se use `execute_sql_file`, crear el temporal dentro del checkout del servidor y pasar una ruta relativa a ese checkout; si se rechaza, cambiar a otra ruta del mismo ambiente sin repetir rutas absolutas fuera del root. Las skills Oracle crean objetos en `DATA` por defecto, califican el owner en el DDL y solo lo cambian si el usuario especifica otro. Una denegación Oracle se reporta; nunca se reintenta bajo el owner del usuario conectado.
- **Alternativas consideradas:** tratar ORA-20987 como rechazo de la vista; repetir el mismo artefacto absoluto; pedir al usuario ejecutar la consulta; dejar el owner al usuario conectado; resolver la ruta interna de forma explícita y usar la ruta APEX equivalente; fijar `DATA` sin override. Se eligen rutas alternativas dentro del ambiente solicitado y `DATA` con override explícito.
- **Impacto y dependencias:** actualiza las instrucciones de diagnóstico, creación de esquema y gobierno DATA, más la documentación del MCP, y cambia el owner predeterminado del generador `ApexSchemaSpec` de `SCOTT` a `DATA`, conservando los overrides explícitos. No altera grants, credenciales, objetos Oracle ni archivos de ambiente. Las operaciones siguen dependiendo de los privilegios efectivos de la credencial y la herramienta.
- **Riesgos y compatibilidad:** el MCP controlado mantiene su restricción de raíz de checkout; herramientas APEX y vistas públicas pueden variar por versión o grants. El owner `DATA` debe ser permitido a la credencial; si no, Oracle devuelve la denegación real y la skill no crea el objeto en otro esquema. No se ejecutan mutaciones para probar permisos.
- **Validación:** inspección de código confirma que `workspace_sql_file()` compara la ruta resuelta con `ROOT`; comparación SHA-256 confirma que las copias instaladas de las skills analizadas coincidían con el checkout al inicio de la revisión. Se inspeccionó el cambio del default del generador a `DATA` y se conserva el parámetro para overrides. No se ejecutó una consulta de producción ni DDL nuevo como parte de esta decisión.
- **Reversión:** revertir los cambios de texto y esta decisión; no requiere rollback Oracle/APEX.
