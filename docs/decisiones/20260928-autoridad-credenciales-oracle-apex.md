# Decisión: permisos Oracle/APEX según credencial configurada

- **Fecha:** 2026-09-28
- **Estado:** vigente
- **Objetivo:** restaurar la ejecución directa por las rutas configuradas sin sustituir los grants reales del DBA por una matriz ficticia de permisos.
- **Decisión:** la solicitud directa define acción, ambiente y alcance. El agente selecciona la credencial configurada para ese ambiente (por ejemplo, `DB_TESTING_*` o `DB_PRODUCTION_*` en `.env` para SQLcl, o el perfil asociado al conector APEX). Oracle/APEX y los permisos efectivos que el DBA/APEX administrator concedió a esa cuenta determinan qué operaciones proceden. Las skills no codifican un usuario ni permisos fijos por ambiente.
- **Validación inicial:** al comenzar, verificar mediante consultas/rutas de solo lectura la identidad y destino reales y, cuando esté disponible, los privilegios de sesión. La inspección es informativa y no pide una aprobación adicional. No ejecutar mutaciones de prueba para adivinar permisos; la operación solicitada recibe la decisión efectiva del servicio.
- **Superficie de herramientas:** que un MCP exponga una operación no concede privilegios; que el usuario tenga credenciales no amplía el alcance pedido. Usar la ruta adecuada para la operación y el ambiente; verificar el destino porque el nombre/rótulo del conector no demuestra qué instancia respondió.
- **Capacidades intencionales:** permitir que SQLcl/MCP envíe DDL/DML/PLSQL Oracle y operaciones APEX solicitadas a la credencial configurada, sin un allowlist de ambiente/objeto en las skills; Oracle/APEX decide grants efectivos. Una auditoría debe distinguir esta conducta autorizada de un error técnico y revisar que el agente mantenga el alcance explícito de la solicitud.
- **Fluidez:** no pedir al usuario que ejecute consultas o ediciones que pueda realizar el agente. No pedir confirmaciones repetidas ni aprobaciones separadas para una operación ya solicitada. Inferir valores razonables; preguntar solo por datos indispensables. Si una ruta falla, intentar otra configurada para el mismo ambiente antes de detenerse.
- **Alternativas consideradas:** conservar matrices fijas por ambiente/usuario; quitar los límites de alcance de la solicitud; dejar que la credencial y su destino reales definan permisos efectivos. Se elige la última opción manteniendo alcance exacto y comprobación de identidad/destino.
- **Impacto:** las operaciones Oracle/APEX quedan disponibles cuando la cuenta configurada tiene grants suficientes y la herramienta implementa esa operación. El executor informa el resultado del servidor; las skills ya no bloquean por reglas locales de ambiente. Se recuperan las fases útiles de diseño y QA sin aprobación artificial ni duplicación de especialistas.
- **Riesgos:** una cuenta con grants amplios puede ejecutar operaciones de alto impacto. El agente respeta el alcance exacto, mantiene evidencia sin secretos e informa resultados reales. No se solicitan ni modifican grants.
- **Compatibilidad:** no fijar versión APEX ni inferir permisos por ambiente; reportar incompatibilidades reales de la ruta elegida. El MCP controlado requiere SQL en su checkout; para otros proyectos se crea el SQL temporal allí o se usa SQLcl configurado.
- **Validación:** inspección estática del routing, descripciones, instrucciones de conexión, guard de despliegue, flujos de diseño/QA y catálogos. `.env.example` queda intacto. No ejecutar pruebas ni conexiones en este cambio.
- **Reversión:** restaurar los cambios de política, routing, documentación y orquestadores si el usuario decide otra política. No modificar grants de cuentas ni configuración de servidores.
