# Decisión: revisión APEX por lote en una conexión

- **Fecha:** 2026-10-15
- **Estado:** vigente
- **Objetivo:** reducir la latencia de una revisión completa de página APEX agrupando las consultas de metadata en una sesión SQLcl.
- **Necesidad:** en TEST, para la página 109.131, diez SELECT ligeros necesitaron una mediana de 114.722 s al abrir una sesión por consulta y 12.083 s al enviarlos en una sesión. El SQLcl `-version` tomó 1.281 s de mediana y la conexión mínima con `select 1 from dual` 10.889 s. DNS y conexión TCP midieron menos de 0.12 s cada una; el costo dominante está en el inicio/login/handshake de SQLcl-Oracle, no en las lecturas. La medición no separa con precisión autenticación de negociación e inicialización del servicio.
- **Alcance:** agregar `execute_readonly_batch` al MCP controlado; limitarlo a 25 SELECT de una línea y 100000 caracteres; validar todo antes de abrir SQLcl; compartir binds enteros; iniciar una transacción de solo lectura; devolver identidad de sesión, esquema y servicio por defecto; separar resultados con marcadores aleatorios de inicio/fin; aislar y reportar ORA por consulta; registrar un digest por SELECT, resultado por consulta y tiempos sin SQL, binds ni datos. Mantener `execute_readonly_query` y todas las rutas de mutación y gates sin cambios de comportamiento. Añadir consultas de snapshot de página comprobadas en TEST y sincronizar instrucciones y catálogos relacionados. No se agregan skills, dependencias, upstreams ni permisos.
- **Decisión:** usar una sola ejecución de `sqlcl_result` con continuación de errores habilitada solo para el lote. El default continúa siendo `whenever sqlerror exit sql.sqlcode rollback`; las mutaciones siguen fail-closed. Una identidad `sys_context` precede las consultas de página en la misma sesión. Los marcadores contienen un token aleatorio por invocación y solo se reconocen cuando una línea coincide exactamente, evitando que texto parecido dentro de datos separe resultados. La vía unitaria continúa disponible para un SELECT aislado.
- **Alternativas:** (1) sesión persistente de SQLcl: no se adopta ahora porque el lote observado ya baja diez conexiones a una; persistencia exige ciclo de vida, limpieza y aislamiento de sesión y credenciales, sin evidencia de que mejore el objetivo frente al lote de una sola llamada. (2) driver Python sin JVM: no se adopta porque implicaría otra ruta y dependencia de conexión; el lote reduce el trabajo de página a una sesión de 12–20 s observados sin migrar credenciales ni reescribir la ejecución SQL. (3) paralelizar consultas con agentes: se descarta porque cada conexión conserva el costo medido cercano a 11 s; aumenta el número de logins, presión sobre el servicio y coordinación, frente a los 12.083 s de una sesión serial.
- **Impacto y dependencias:** requiere el runtime SQLcl existente, el perfil TEST/Producción seleccionado en `.env` y las vistas públicas `APEX_APPLICATION_*` accesibles a la cuenta. La herramienta no hace `doctor_report`, inspección de privilegios ni consultas de inventario; Oracle determina los permisos efectivos. La bitácora agrega un evento por lote que contiene hashes, resultados y tiempos. La auditoría local es JSONL en `.bitacora.json` y no se versiona.
- **Permisos y datos:** la nueva operación solo acepta SELECTs validados y corre con `SET TRANSACTION READ ONLY`; no es sandbox para funciones definidas por usuario con efectos laterales. Esta tarea ejecutó exclusivamente lecturas contra TEST, aplicación 109, página 131. No se consultó ni modificó Producción, ni se ejecutaron DDL/DML o scripts de instalación. El perfil proviene de `.env`; credenciales y endpoint no se registran ni se incluyen en el informe.
- **Riesgos:** una consulta lenta o con mucha salida puede prolongar la sesión; errores por consulta se devuelven junto con las demás. Los límites reducen lotes accidentales grandes, pero no validan la finalidad de funciones invocadas en un SELECT. Un cliente MCP ya activo puede necesitar reiniciarse para descubrir la nueva herramienta. La medición de `Elapsed` del script tiene resolución insuficiente para atribuir tiempos subsegundo a Oracle.
- **Compatibilidad:** la firma de las diez herramientas existentes se conserva y se agrega una nueva. La API individual `execute_readonly_query` no cambia. La sintaxis de continuación se verificó en el SQLcl instalado en Windows y se cubre con pruebas. Las consultas del snapshot se contrastaron con `ALL_TAB_COLUMNS` en TEST (APEX 24.2); no usan vistas internas `WWV_FLOW_*`.
- **Validación:** `sqlcl -S /nolog` y `exit` terminó con códigos 0 en tres intentos (5.008 / 3.649 / 4.694 s; mediana 4.694 s). DNS tardó 0.116 / 0.000 / 0.000 s y TCP 0.104 / 0.107 / 0.111 s. El script externo, tres repeticiones, midió para diez SELECT ligeros 112.144 / 114.722 / 115.082 s en sesiones separadas y 11.870 / 12.083 / 12.449 s en una sesión; `-version` tomó 1.268 / 1.281 / 1.356 s y la conexión mínima 10.749 / 10.889 / 10.901 s. Con las diez consultas reales del snapshot, la repetición posterior midió 162.547 / 164.686 / 169.599 s con sesión por consulta y 19.125 / 19.255 / 19.306 s en una sesión. FastMCP local ejecutó el lote completo de 109.131 una vez con identidad y binds TEST: 10 resultados, ningún ORA, `profile_load=1 ms`, `sqlcl_process=19480 ms`, `route_total=19483 ms`. Otra lectura produjo intencionalmente `ORA-00904` en la primera SELECT y éxito en la siguiente. El cronómetro SQLcl reportó `0.0 s` dentro de Oracle por su resolución; no se interpreta como cero real. F2 comprobó las vistas y columnas mediante `ALL_TAB_COLUMNS`; el detalle está en `skills/apex-database-diagnostics/references/page-snapshot-queries.md`.

Después conserva las diez firmas y agrega `execute_readonly_batch(queries: list[str], environment: str | None = None, bind_variables: dict[str, int] | None = None, include_identity: bool = True)`. - **Pruebas y gates:** el primer run enfocado falló en rojo antes de implementar la herramienta; la salida se guardó en `.codex-tmp/readonly-batch-tests-red.log`. Tras la implementación, las 11 pruebas nuevas pasaron; salida en `.codex-tmp/readonly-batch-tests-green.log`. En F5, `pytest tests/` pasó 544 pruebas con cobertura 60.40%; `run_ci_checks.py` PASS; `audit_skill_ecosystem.py` PASS con N/A TLS; `audit_markdown_links.py` 0 enlaces locales rotos y N/A TLS justificado; `audit_quality_score.py` 100/100; pre-commit PASS en las 11 rutas del cambio. La primera ejecución de CI detectó la anotación ausente `list[str]` en `statements`; se corrigió y se repitieron los gates completos. La revisión independiente registrada para la implementación inicial examinó su política y diff, no ejecutó SQL ni editó archivos, y no encontró defectos bloqueantes; no corresponde a esta corrección. Confirmó como limitaciones: compatibilidad probada solo en TEST APEX 24.2; la transacción de solo lectura no bloquea funciones SELECT con efectos secundarios; y un error de escritura de la bitácora puede hacer fallar la llamada después de ejecutar las consultas. La auditoría de seguridad confirma validación antes de conexión, límites, transacción de solo lectura, continuación exclusiva del lote, bitácora sin SQL/binds/datos, y cero cambios AST en las nueve funciones de mutación/gates comprobadas.
- **Reversión:** revertir el commit de la herramienta y pruebas, y el commit de documentación asociado. No requiere restaurar datos Oracle/APEX porque la implementación solo lee. Si el MCP ya está registrado localmente, reiniciarlo tras revertir para refrescar la lista de herramientas.
- **Descontinuación:** revisar esta decisión si el lote de página supera 25 s de forma repetible, si el costo interno de Oracle domina las mediciones o si se adopta una sesión persistente/driver con evidencia de rendimiento y controles equivalentes. En ese caso conservar los SELECT verificados, el contrato de solo lectura y el registro sin datos.

## Manejo de fallos y límites conocidos

- Cada consulta requiere sus dos marcadores exactos. Si falta el inicio o el fin, devuelve `OUTPUT_INCOMPLETE`; una salida vacía entre ambos marcadores sí es una salida completa.
- Un dato cuyo texto contenga `ORA-xxxxx:` o `SP2-xxxx` marca la consulta como error, por falla del lado seguro.
- Los ORA dentro de una consulta producen `ORACLE_ERROR` y los mensajes SQL*Plus/SQLcl `SP2-xxxx` producen `SQLCL_ERROR`. Estos fallos no cancelan las consultas restantes.
- Cualquier ORA emitido antes del primer marcador produce `CONNECTION_FAILED` en el lote y en todas sus consultas, también cuando `include_identity=False`: todavía no comenzó la salida de una consulta. Esto incluye los errores de autenticación `ORA-01017`, `ORA-28000` y `ORA-28001`; se valida con salidas simuladas y no se prueban credenciales inválidas contra Oracle.
- El lote solo declara `ok=true` cuando todas las consultas terminan en `SUCCESS` y, si se solicitó, se obtuvo identidad. Un fallo de escritura de bitácora conserva los resultados y añade `audit_persisted=false` y un aviso; no cambia el estado SQL de las consultas.
- La detección global se limita a errores ORA anteriores al primer marcador. El lote no puede atribuir mensajes de conexión sin código Oracle ni reconstruir una salida truncada después de emitir los marcadores. La detección funcional se prueba con salidas simuladas; la única comprobación real de “no conectado” ejecuta `SELECT` bajo `sqlcl -S /nolog`, sin credenciales ni conexión Oracle.
