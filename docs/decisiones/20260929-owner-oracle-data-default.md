# Decisión: propietario DATA predeterminado para solicitudes Oracle

- **Fecha:** 2026-09-29
- **Estado:** vigente
- **Objetivo:** hacer consistente y visible en la ruta de entrada la regla de que los objetos Oracle se crean, modifican o eliminan en `DATA` si el usuario no especifica otro esquema.
- **Evidencia:** `apex-schema-automation-safe` y `oracle-data-change-governance-final` ya definían `DATA`, pero el coordinador y su prompt de agente no repetían la regla. El usuario reportó que una tabla solicitada sin propietario terminó en el esquema de la cuenta conectada. No se recibió el SQL ni el registro de esa ejecución, por lo que no se atribuye el desvío a una herramienta específica.
- **Decisión:** el coordinador resuelve el propietario como `DATA` para objetos Oracle salvo indicación explícita distinta; se conservan excepciones específicas de gobierno, como objetos de backup en el esquema del usuario conectado. El enrutamiento, la automatización de esquemas y el orquestador de datos transmiten esa decisión. Todo DDL (CREATE, ALTER, DROP y CREATE OR REPLACE) y DML relacionado debe calificar el propietario seleccionado. `SESSION_USER` y `CURRENT_SCHEMA` son contexto, no sustitutos del propietario elegido. Si Oracle rechaza el propietario, se reporta el error sin reintentar bajo el usuario conectado.
- **Alternativas consideradas:** dejar el default únicamente en la skill especialista; cambiar `CURRENT_SCHEMA` a `DATA`; reescribir SQL automáticamente en el runtime. Se conserva la regla declarativa en el punto de entrada y en los especialistas. Cambiar sesión o transformar SQL no es necesario para lograr que los artefactos se califiquen correctamente y podría alterar semántica ajena al objetivo.
- **Impacto y dependencias:** actualiza el coordinador, prompt del agente, routing, automatización de esquemas y orquestador de datos. Añade una prueba de contrato que detecta la pérdida de la regla en esos puntos. No cambia conexiones, permisos, objetos Oracle ni el SQL runtime.
- **Riesgos y compatibilidad:** las instrucciones guían al agente; no son un parser/validador de SQL en tiempo de ejecución. La ejecución sigue dependiendo de que el agente genere DDL/DML calificado y de los privilegios Oracle de la credencial. Un owner explícito del usuario tiene precedencia.
- **Validación:** revisión independiente sin bloqueos; `scripts/audit_skill_ecosystem.py` y la auditoría de calidad pasaron (100/100); `scripts/run_ci_checks.py` pasó con 492 pruebas, 56,14% de cobertura combinada, Black, isort, flake8, mypy, Bandit, detect-secrets y `git diff --check`. El test enfocado del generador/routing pasó también (33 casos).
- **Reversión:** revertir las instrucciones, la prueba, la entrada del changelog y esta decisión. No requiere rollback Oracle.
